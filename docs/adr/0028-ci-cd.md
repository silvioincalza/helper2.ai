# 0028 — CI/CD: GitHub Actions, PR checks, OpenBao OIDC, staging on main, approved prod on a release

**Status.** Accepted (2026-10-27). **Builds on:** [0007](0007-configuration-and-secrets.md), [0027](0027-runtime-topology.md)

## Context
The repository is public. The cluster's application programming interface (API) and the image registry (Harbor) are reachable
only on a private WireGuard network. Every change on `main`
should reach staging without manual steps. Prod should run only released versions, and only after a person
approves: `main` may carry unfinished work that staging shows and users must not see yet. Code from a fork must
never run where deploy credentials exist, and GitHub must hold no long-lived secret.

## Decision
1. **Continuous integration (CI) on every pull request (PR)** — `ci.yml`, GitHub-hosted runners:
   - frontend: `npm ci`, generate API types, lint, typecheck, Vitest, build;
   - backend: `./gradlew test` (Testcontainers with PostgreSQL and Redis);
   - chart: `make -C deploy/k8s chart-check` (`helm lint --strict`, `helm template | kubeconform -strict`
     for staging, prod, and prod with the off-site backup on);
   - PRs only: app image build without push; Postgres image build plus a check that `postgres.image.tag`
     changed when `deploy/postgres` changed; `terraform fmt -check` and `validate` against a stub of the edge
     module; D2 diagrams re-rendered with d2 v0.9.0 and compared with the committed SVG files.
2. **Continuous delivery (CD) on every push to `main`** — `cd.yml`: CI runs again, then the `image` job on
   the self-hosted runner builds and pushes `make postgres-image` and `make image` (each only when its tag is
   not in Harbor yet). The image tag is the first 12 characters of the commit, built from `git archive`.
3. **Staging on every push, prod on a release.** `deploy.yml` (reusable, `workflow_call` only) runs `make diff`,
   `make deploy`, `make status` for one GitHub environment. `cd.yml` calls it for `staging` after each push to
   `main`, and never for prod. `release.yml` calls it for `prod` when a release tag `vX.Y.Z` passes its checks
   ([0029](0029-release-versioning.md)), with that tag's commit: an image built when the commit reached `main`
   and already run on staging. A `staged` job first waits for that commit's CD run and goes on only when it
   passed: a commit whose staging deploy failed, or never ran, cannot reach prod. The `prod` environment has a required reviewer and allows branch `main` and
   tags `v*` only.
4. **OpenBao login with OpenID Connect (OIDC).** `.github/actions/bao-login` asks GitHub for the job's OIDC
   token (audience = the OpenBao address) and logs in at `auth/helper2/jwt` with a role bound
   to the repository and to the branch or environment: `deploy` (reads `ci/harbor`), `deploy-staging`
   (reads `ci/staging`), `deploy-prod` (reads `ci/prod`). The prod role can log in only after the approval.
5. **Tag checks in the deploy job.** The tag must be 12 hex characters, no branch or tag may have that name,
   it must resolve to a commit on `main`, and the chart is checked out from that same commit. Manual runs
   take an environment and a tag (redeploy, rollback); prod with an empty tag promotes what staging runs now.
6. **One runner per job.** The self-hosted runner registers a just-in-time (JIT) runner
   for one job and wipes its workspace after it. It holds no kubeconfig and no OpenBao token of its own.
   `cd.yml` has no `pull_request` trigger; third-party actions are pinned to commit hashes (SHA).
7. **Deploys are not canceled.** `concurrency: deploy-<env>` with `cancel-in-progress: false`, because an
   interrupted `helm upgrade --wait` leaves the release blocked.

## Consequences
- A green PR has run the same checks that guard `main`; CD repeats CI before it builds anything.
- Pipeline and workstation run the same `Makefile` targets, so the deploy is not described twice.
- Prod cannot get an untested image: a release tag names a commit of `main`, which staging got first, and image
  tags are never rebuilt.
- Prod changes only on a release (or a manual run). Work in progress can live on `main` and on staging, with no
  feature flag to keep it from users.
- A push to `main` no longer leaves a prod job waiting for approval.
- The deployer's Kubernetes token does not expire; it sits in OpenBao and in the namespace.
- Terraform stays manual (`make bootstrap`): it needs the Cloudflare token and owns the namespace and tunnel.
- There are no browser end-to-end tests in CI.

## Alternatives considered
- GitHub-hosted runners for deploys — they cannot reach the private network without opening the API or Harbor.
- GitHub Actions secrets for the kubeconfig and app env — long-lived values in GitHub; OIDC avoids them.
- Argo CD or Flux (GitOps) — a controller in the cluster and a second repository of state for one app.
- Build on every deploy — prod would run a fresh build, not the image staging tested.

## Code
- `.github/workflows/ci.yml`, `cd.yml`, `deploy.yml` — the pipeline; `release.yml` — the prod deploy of a release.
- `.github/actions/bao-login/action.yml` — OIDC login to OpenBao.
- `deploy/k8s/Makefile` — `image`, `postgres-image`, `chart-check`, `diff`, `deploy`, `status`, `rollback`.
- `deploy/k8s/terraform/rbac.tf` — `deployer` Role, and the prod deployer's read of staging's Deployment.
- `deploy/k8s/CI.md` — one-time setup of GitHub, the runner and OpenBao.
