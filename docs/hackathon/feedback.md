# Feedback on Nebius Token Factory and NVIDIA Nemotron

For the Devpost form ("Most Valuable Feedback"). Measured during the build, 22–27 Oct 2026.

## Nebius Token Factory
- **What I used it for:** three runtime calls per guide question (plan, choose, reason check) and the Scout's background enrichment, all through Spring AI's OpenAI-compatible client. No custom HTTP code was needed.
- **Zero to first working call (time, steps, blockers):** under 30 minutes, no blocker: sign up, create a key, list models with `GET /v1/models`, call. One concrete trap: with Spring AI 2 the base URL must include `/v1` (`https://api.tokenfactory.nebius.com/v1`), because Spring AI uses it as-is. A line about this in the "OpenAI-compatible clients" docs would save time.
- **What worked well:** the OpenAI-compatible API worked with an off-the-shelf client; `GET /v1/models` made it easy to find the exact model ids; in the runs we logged up to 26 Oct (about 45 questions), every model failure was a JSON parsing error; we saw no HTTP errors, rate limits or timeouts.
- **What needs work:** reasoning tokens count against `max_tokens` (Nemotron 3 Super: 408 of 567 completion tokens in a small test, `usage.completion_tokens_details.reasoning_tokens`). With our 2048 limit the answer JSON was cut off midway and looked like a "bad JSON" problem; it took us a while to find. A note in the docs, or a separate limit for reasoning, would help. On 27 Oct the service was overloaded during our final evaluation: a direct call returned HTTP 529, and the same choose request took up to 11.5 s instead of 1.3 s an hour earlier. A status page or a `Retry-After` header would help clients back off. Model ids use different casing styles (`nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B` vs `nvidia/nemotron-3-super-120b-a12b`), so you have to copy them exactly from `/v1/models`. `response_format` with a JSON schema worked for Nemotron 3 Super but not for Nano (see below); a per-model table of supported parameters would help.
- **Would I build with it again, and why:** yes. The OpenAI-compatible API meant zero custom client code, and open NVIDIA models let us pick a small fast model and a larger reasoning model for each step.

## NVIDIA Nemotron (Nano for planning, 3 Super for choosing and for the reason check)
- **What I used each model for:** Nano turns a need in any language into an English search query, a short list of hard requirements ("free", "self-hosted", "MIT or Apache licence") and a flag for "wants papers/news". Super chooses at most 3 of 24 real candidates, explains why, and quotes the candidate's own text for the pick and for each requirement. A deterministic validator then keeps only quotes that appear word for word.
- **Latency and output quality, Nano vs Super:** measured on our Mac against Token Factory (backend log `guide timings`). Nano planning: p50 1.1–2.8 s, max 5.7 s. Super choosing over 12 candidates: p50 4.5–7.4 s, max 8.8 s without retries, 28.6 s with a retry. Whole guide answer over 24 candidates with thinking on: p50 15.5 s, p90 19.8 s locally, and p50 21.0 s, p90 46.4 s on the live demo. With thinking off (see below): p50 10.9 s, p90 17.4 s on the live demo while Token Factory was overloaded ([docs/evaluation.md](../evaluation.md)). Nano's Italian → English planning worked on every Italian query we tried (b14). Nano tends to list the resource kind as a requirement ("MCP server", "Postgres", "small; open"), which we filter out in code.
- **Structured (JSON) output reliability:** Nano returned valid JSON for every planning call we logged (about 45 calls). Super did not always: in one full run, 3 of about 21 choose calls failed to parse on the first try (`MismatchedInputException` ×2, `StreamReadException` ×1), and one question failed on both tries. After we added a nested `checks` array to the schema, 2 of the first 3 questions in the next run failed twice. Root cause, found with a direct API call: most failures were `UnexpectedEndOfInputException`, i.e. the JSON was cut off because Super's reasoning tokens used up our 2048 `max_tokens`. Fix: `response_format: json_schema` for Super plus a separate 8192 limit for that call; after it, the next full run had 0 failed answers and 0 retries over 40 model calls (before: 2 of 20 answers lost). With `json_schema`, Nemotron Nano returned `{"picks": [{"candidateKey": "c2", "quote": "…"` followed by whitespace until the token limit, so we keep Nano on the prompt-based format (it never failed that way).
- **Instruction following:** Super often recommended articles, papers or news when the user asked for a tool, although the system prompt forbids it (7 of 17 top picks in one run). A deterministic filter in retrieval fixed it: by our own judgment, relevant top picks went from 8/17 to 11/12. The validator removed 3–5 of Super's suggestions per 20-question run (7–11%): invented or too-short quotes, or wrong types.
- **Thinking on vs off (27 Oct 2026, same 20 questions, same 24 candidates each, [run 17](../eval/run-17-thinking.md)):** thinking tokens caused most of the latency. Super choosing: about 10 s with thinking, 1.3 s without (1,772 vs 97 completion tokens on one question). Nano planning: 2.5 s vs 0.5 s. With thinking, the same choose request at temperature 0 gave different picks when repeated; without it every repeat was identical (4 queries × 2), and the top pick was better on 3 questions and worse on 1. We now turn thinking off with `chat_template_kwargs.enable_thinking=false` for every guide call ([ADR 0016](../adr/0016-guide-reason-check.md)). The cost: Super says "nothing fits" more often (an AI pick on 13 of 19 real questions instead of 17).
- **Reason check (Super, thinking off):** a second call compares each reason with its quote and the resource's own text. 9 of 9 real reasons were supported and 9 of 9 reasons with an added false claim ("free", "works offline", "10k stars", "MIT licensed") were rejected, at 0.9–1.1 s per call. In the final run, 30 of 31 reasons were supported.
- **Nemotron 3.5 Lightning (tried 26 Oct 2026 as a relevance scorer for 24 candidates, prompt-based JSON):** its output could not be parsed as JSON in 2 of 2 runs, so we did not use it. Nano did the same task with valid JSON, but its scores were unstable at temperature 0 and it took 4–8 s, so we let Super choose from more candidates instead ([ADR 0015](../adr/0015-ai-guide-evidence-gate.md)).
- **What needs work:** Nano with guided JSON decoding (whitespace loop); Super's reasoning length is hard to budget (it made a 7 s call take 18–28 s when a retry was needed); with thinking on, output is not repeatable at temperature 0. The `enable_thinking` switch is easy to use but hard to find: one line per model in the Token Factory docs would help.
- **Would I build with it again, and why:** yes. Nano is fast and reliable for planning. Super with thinking off chooses well in about a second, gives the same answer when repeated, and is a good judge for checking another call's claims.
